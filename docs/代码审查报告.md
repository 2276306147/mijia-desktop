## 一、P0 阻断级

### A1　所有业务请求都没有超时，网络异常会拖垮界面

- **位置**：`mijiaAPI/apis.py:321`（`self.session.post(url, data=params)`）、`:283` / `:300`（登录相关 `requests.get`）、`mijiaAPI/devices.py` 中 `get_device_info` 的 `requests.get`
- **原因**：只有扫码长轮询写了 `timeout=120`（`apis.py:291`），其余请求全部用 `requests` 默认值 —— 即**永不超时**。
- **影响**：DNS 污染、TCP 黑洞、公司代理半死时，worker 线程会永久阻塞。`QThreadPool` 默认大小等于 CPU 核数（低配 Windows 只有 2–4 个），几次点击后线程池被占满，表现为「点什么都没反应、也没有报错」，只能杀进程。这是最难自查的一类故障。
- **修复**：在 `app/core/service.py` 顶部（导入 `mijiaAPI` 之前）统一注入默认超时，一处覆盖所有调用：

```python
import requests

_orig_request = requests.sessions.Session.request

def _request_with_timeout(self, method, url, **kwargs):
    kwargs.setdefault("timeout", (5, 20))   # connect, read
    return _orig_request(self, method, url, **kwargs)

requests.sessions.Session.request = _request_with_timeout
```

`requests.get()` 内部同样走 `Session.request`，所以规格拉取、登录接口都会被覆盖；长轮询显式传了 120，`setdefault` 不会覆盖它。

### A2　新建账号后取消扫码，账号会「消失」

- **位置**：`app/core/service.py:288` `start_login()` 中的 `path.unlink(missing_ok=True)`
- **原因**：占位文件 `{}` 会让 `mijiaAPI.__init__` 因缺字段崩溃，所以登录前先删掉。但**删除后没有任何兜底**：用户关掉二维码窗口、或二维码获取失败，文件就永久没了；而账号列表是靠扫目录得到的，于是账号从列表里消失。
- **影响**：用户刚建好账号、点了取消，回头发现账号没了，还会以为「新建账号按钮坏了」——和这次反馈是同一类观感。另外 `_get_qr_login_data()` 抛网络异常时同样会删文件。
- **修复**：登录写入临时文件，成功后再原子替换，失败保留占位：

```python
login_path = path if self.accounts.has_credentials(name) else path.with_name(path.stem + ".login")
api = mijiaAPI(auth_data_path=login_path)
...
def finish_login(self, flow, login_path, final_path):
    flow.wait()
    if login_path != final_path:
        os.replace(login_path, final_path)
    self.reset()
```

失败时删除 `.login` 临时文件即可，正式占位文件始终在。

## 二、P1 高级

### B1　DEBUG 日志会把 Token 明文写进日志文件

- **位置**：`mijiaAPI/apis.py:154` `logger.debug(f"认证数据: {self.auth_data}")`；触发入口：`app/ui/pages/settings.py` 的日志级别下拉框
- **原因**：上游在保存凭证后用 DEBUG 打印整个 `auth_data`，其中包含 `serviceToken` / `passToken` / `ssecurity`。
- **影响**：用户一旦把日志级别切成 DEBUG（排查问题时最常见），`%APPDATA%\MijiaDesktop\logs\app.log` 里就是可直接登录账号的凭证。用户把日志发到群里求助 = 账号被接管。
- **修复**：给 `mijiaAPI` logger 加脱敏过滤器，并禁止把该 logger 设到 DEBUG：

```python
class _Redact(logging.Filter):
    def filter(self, record):
        if "认证数据" in record.getMessage():
            record.msg, record.args = "[认证数据已脱敏]", ()
        return True

logging.getLogger("mijiaAPI").addFilter(_Redact())
```

设置页对 DEBUG 选项加提示，或把 `mijiaAPI` logger 的级别锁在 INFO 以上。

### B2　GPL-3.0 许可证没有随二进制分发

- **位置**：`build/mijia_desktop.spec:67`（`datas` 只有 `app/resources`）；`build/installer.iss`（只打包 `dist\MijiaConsole\*`）
- **原因**：仓库根有 `LICENSE`，但打包时没带进去，安装目录里没有许可证文本。
- **影响**：GPL-3.0 要求分发二进制时附带许可证与源码获取方式；对外分发（尤其公开发 Release）属于合规瑕疵。
- **修复**：CI 在压缩前执行 `Copy-Item LICENSE dist/MijiaConsole/`，并在 spec 中加 `(LICENSE, ".")`；同时把 `mijiaAPI` 的来源与许可证写进「关于」页（已部分存在）。

### B3　依赖未锁定，构建不可复现

- **位置**：`requirements.txt`（`PySide6-Essentials>=6.6.0`、`mijiaAPI>=5.0.0`）、`requirements-build.txt`（`pyinstaller>=6.6`）、CI 每次 `pip install` 重新解析
- **原因**：没有 pin、没有 lock 文件（`mijiaAPI` 仓库有 `uv.lock`，本桌面项目没有）。
- **影响**：今天能出包，下周 PySide6 6.13 或 PyInstaller 6.17 一发布就可能 hook 不兼容/build 失败；用户之间也无法复现同一个二进制。这次已经踩过 PySide6 版本相关的坑。
- **修复**：锁定到已跑通的组合（`PySide6-Essentials==6.12.0`、`mijiaAPI==5.0.0`、`pyinstaller==6.16.0`），或改用 `uv lock` + `uv sync --frozen`；升级走单独的 PR 验证。

### B4　依赖上游 3 个私有方法，版本升级即可能断裂

- **位置**：`app/core/service.py:288` 起，调用 `api._get_qr_login_data()`、`api._complete_qr_login()`、`api._refresh_token()`
- **原因**：公开接口只有 `login()`（会自己打印终端二维码并阻塞），GUI 需要「拿二维码图片 + 后台等待」，只能走私有方法。
- **影响**：`mijiaAPI` 任意小版本重构这三个方法，扫码登录直接不可用，且属于运行时才暴露的错误。
- **修复**：包一层 `MijiaAdapter` 集中处理，启动时用 `hasattr` 做能力检查并给出可读错误；同时在 `requirements` 中锁 `<6`；向上游提 issue/PR，建议暴露 `qr_login_begin()/qr_login_wait()` 公共 API。

### B5　一次请求提交设备的全部属性，缺少分片

- **位置**：`app/core/service.py:386` `read_props()`
- **原因**：把该设备所有可读属性拼成一个 `params` 列表一次性 `get_devices_prop`。
- **影响**：属性多的设备（网关、空调伴侣常见 30–60 个属性）可能超过服务端单次参数上限或超时——**具体阈值未验证**，但一旦触发就是「设备页永远转圈/报错」。分片是无害的保守做法。
- **修复**：按 20 条一批拆分，合并结果；失败批次单独重试一次。

### B6　写属性、执行动作、跑场景都没有防重复与节流

- **位置**：`app/ui/pages/devices.py:435` `_write()`、`:465` `_run_action()`；`app/ui/pages/scenes.py` 的执行按钮
- **原因**：按钮/滑块在请求飞行期间不置灰，也没有 in-flight 集合。
- **影响**：连点两次「执行」= 设备收到两条指令（喂食器、窗帘这类动作不可重入，后果明显）；拖动滑块松手过快会连续下发多条写请求，触发网关限流或状态错乱。
- **修复**：为每个 `(did, prop/action)` 维护 in-flight 标记，飞行期间禁用控件；写属性用 300–500ms 防抖合并。

## 三、P2 中级

### C1　配置文件被改成非对象 JSON 会导致启动崩溃

- **位置**：`app/core/config.py:60` `Config.load()`
- **原因**：`json.loads` 成功但结果是 list/字符串时，`data.items()` 抛 `AttributeError`，未被捕获。
- **影响**：用户手改 `settings.json` 或磁盘损坏（内容变成 `[]`）后，应用每次启动即崩，且没有提示。
- **修复**：`if not isinstance(data, dict): data = {}`，并把解析异常写入日志。

### C2　窗口几何未校验，可能恢复到屏幕外

- **位置**：`app/ui/main_window.py:484` `_restore_geometry()`
- **原因**：直接 `int(geom["w"])`，不校验类型；也不判断坐标是否落在当前屏幕内。
- **影响**：① 手改配置成字符串会 `ValueError` 崩溃；② 拔掉外接显示器后窗口恢复到不存在的坐标，表现为「程序启动了但看不到窗口」。
- **修复**：用 `QGuiApplication.screens()` 判断可见区域，越界则居中；`int()` 包 try/except。

### C3　服务层不是线程安全的

- **位置**：`app/core/service.py:248` `api` 属性、`_refresh_token` 调用链
- **原因**：`self._api` 懒加载无锁；多个 worker（设备刷新、场景、统计）可能同时发现 `_api is None` 并各自构造 `mijiaAPI`，进而并发触发 token 刷新。
- **影响**：并发构造时后写的实例覆盖前者，`requests.Session` 的 Cookie/Token 状态可能不一致；并发 refresh 可能触发服务端风控。
- **修复**：加 `threading.Lock` 保护构造与 refresh；或把网络调用收敛到单线程队列（更彻底）。

### C4　每次刷新设备都多打一次家庭列表接口

- **位置**：`app/core/service.py:321` `load_snapshot()`
- **原因**：先 `api.get_homes_list()`，随后 `api.get_devices_list()`（其内部 `home_id=None` 时又调了一次 `get_homes_list()`）。
- **影响**：每次刷新 4 次往返变 3 次（约多 25% 延迟），弱网下体感明显。
- **修复**：拿到 homes 后按 `home_id` 逐个 `get_devices_list(home_id=...)`，或直接用 `_get_devices_list` 复用。

### C5　登录 worker 不可取消，最长占用线程 120 秒

- **位置**：`app/ui/login_dialog.py` 的 `_wait()` → `service.finish_login()`
- **原因**：`requests` 阻塞在长轮询里，没有取消机制；关闭对话框只是忽略回调。
- **影响**：低配机器线程池只有 2–4 个，用户反复开关登录窗口会逐渐占满，之后所有异步操作假死（叠加 A1 更糟）。
- **修复**：给长轮询传更短的分段超时并轮询取消标志；或登录使用独立线程，不占全局池。

### C6　登录成功后在 worker 线程里重置全局状态

- **位置**：`app/core/service.py` `finish_login()` 中的 `self.reset()`
- **原因**：`reset()` 清空 `_api` / `_snapshot`，而主线程可能正在读 `snapshot` 渲染设备树。
- **影响**：偶发「刚登录后设备树闪一下变空」或正在进行的请求报「未登录」。
- **修复**：把 `reset()` 与后续刷新调度回主线程（`QMetaObject.invokeMethod` 或信号），或在 reset 后立刻触发一次完整刷新。

### C7　动作执行后不刷新属性，界面状态可能过期

- **位置**：`app/ui/pages/devices.py:465` `_run_action()`
- **原因**：只提示「已发送」，不回读属性。
- **影响**：执行 `toggle` 后开关仍显示旧状态，用户以为没生效又点一次，形成反向操作。
- **修复**：动作成功后 1s 触发一次 `_refresh_props`（复用现有逻辑）。

### C8　全局移除了焦点框，键盘操作不可见

- **位置**：`app/ui/theme.py:80` `* { outline: none; }`
- **原因**：为了美观全局关闭 outline，未给 `:focus` 补替代样式。
- **影响**：Tab 键导航时看不到焦点位置，键盘用户/无障碍场景不可用；也不符合 Windows 应用的基本预期。
- **修复**：改为只对特定控件关闭，或补 `QPushButton:focus { border: 1px solid accent; }` 等焦点态。

### C9　托盘菜单在 `aboutToShow` 里清空并重建自身

- **位置**：`app/ui/main_window.py:249` `_rebuild_tray_menu()`
- **原因**：在菜单即将显示的信号里 `clear()` 再 `addAction`。
- **影响**：这是已知的脆弱写法，部分 Windows/Qt 组合会出现菜单空白、闪烁或崩溃（**未实机验证**）。
- **修复**：改为在数据变化时（刷新完成、收藏变更）重建菜单并 `setContextMenu()`，`aboutToShow` 只做轻量更新。

### C10　耗材百分比是猜的，可能严重误导

- **位置**：`app/ui/pages/consumables.py:22` `_percent()`
- **原因**：把 0–100 的任意数值都当作百分比。
- **影响**：某些设备返回「剩余 30 天」→ 显示 30% 进度条；返回「已用 5 次」→ 显示 5%。用户会误判耗材寿命。
- **修复**：仅在字符串含 `%` 或字段明确为 `percentage` 时才画进度条，否则只显示原文。

### C11　只读枚举显示原始数值而不是描述

- **位置**：`app/ui/widgets.py:212` `PropertyRow`
- **原因**：只读分支直接 `label(self._format(value))`，没有查 `value-list`。
- **影响**：传感器状态显示 `2` 而不是「影院模式」，可读性差。
- **修复**：只读时按 `value-list` 反查描述，找不到再回退数值。

### C12　`last_page` 只写不读，是伪功能

- **位置**：`app/ui/main_window.py:372` 写入；启动流程未读取
- **原因**：保存了上次页面索引，但 `__init__`/`bootstrap` 从不恢复。
- **影响**：用户每次启动都回到设备页，与设置里的字段预期不符（且是无用磁盘写入）。
- **修复**：启动时 `goto(min(config.last_page, len(NAV)-1))`，或删掉该字段。

### C13　顶层包名叫 `app`，安装后会污染 site-packages

- **位置**：`pyproject.toml` `[tool.setuptools.packages.find] include = ["app*"]`
- **原因**：`app` 是极通用的名字。
- **影响**：`pip install .` 会把 `app/` 装进全局 site-packages，与任何同名包冲突；也容易被其他工具误导入。
- **修复**：重命名为 `mijia_desktop/`（同时改入口点与 spec 的 `pathex`），或保持不发布到 PyPI、只在仓库内运行。

### C14　CI 只打包，不跑静态检查与测试

- **位置**：`.github/workflows/build-windows.yml`
- **原因**：没有 `ruff check` / `pytest` 阶段。
- **影响**：语法错误、未定义变量、明显回归要等 Windows 构建（5 分钟）甚至用户实测才暴露——这次 `stdout=None` 就是这样漏出去的。
- **修复**：加一个 `lint` job（ubuntu，10 秒）：`pip install ruff && ruff check app`；后续补 pytest 再接入。

### C15　错误提示是模态框，批量失败会连环弹窗

- **位置**：`app/ui/pages/devices.py` `_on_error()` 及其调用点
- **原因**：任何一次写失败都 `QMessageBox.warning`。
- **影响**：刷新时若多台设备异常，用户要连点十几次「确定」；自动化/远程桌面场景更糟。
- **修复**：区分「操作级错误」（状态栏 + 行内红字）与「会话级错误」（模态框）；模态框加「不再提示」。

### C16　没有重试与退避

- **位置**：`app/core/service.py` 所有网络方法
- **原因**：一次失败直接上抛到 UI。
- **影响**：米家接口偶发 5xx / 超时（尤其弱网），用户看到「操作失败」，重试要手动再点一次。
- **修复**：对幂等读操作做 2 次指数退避重试（0.5s/1.5s）；写操作不自动重试，但提示「重试」按钮。
